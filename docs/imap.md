# IMAP and SMTP accounts

How a plain IMAP/SMTP account (Fastmail, iCloud, a work server, any provider) fits beside the Gmail accounts, which keep the Gmail API. DESIGN.md keeps the decisions in short; this is the detail. Written 2026-11-24.

## The goal

A person adds an IMAP/SMTP account from Settings › Accounts, and then reads, searches, files, flags, writes and sends mail in it as they do in a Gmail account. Agents' tools work over it wherever the operation makes sense. Calendars stay Google's: an IMAP account has none.

## One model, two providers

Postrinch's model was written for labels, and Gmail's labels are a superset of folders. So an IMAP account is shown through the same model rather than beside it:

- **A folder is a label.** Each selectable IMAP folder is a `Label` of the account, but Gmail's All Mail (below). A message's labels are the folders holding a copy of it that are labels.
- **The special folders are the system labels, with the same ids in every account.** `INBOX`, `SENT`, `DRAFT`, `TRASH` and `SPAM` name the inbox, Sent, Drafts, Trash and Junk whatever a provider calls them (`SystemLabel::provider_id`). So "archive is removing `INBOX`", "trash is adding `TRASH`" and the rules' tests hold for every account by contract, not by luck. The folders are found by SPECIAL-USE (RFC 6154) or, failing that, by the names providers use (`Sent Items`, `Deleted Messages`, `Junk E-mail`…), and the person can choose them in the account's settings.
- **A user folder's label id is minted** (`f` and 12 hex digits) when Postrinch first sees it, and kept in the folder's state with its name on the server. Renaming a folder from Postrinch keeps its id, so its messages, prefs and the rules naming it stay attached. A folder renamed elsewhere keeps its id too, when the sync can tell it is the same folder (see Sync).
- **Categories, Important and Gmail's search** don't exist for IMAP accounts. The Inbox view shows an account without categories whole (as its Primary), the category tabs and rule actions are offered only for accounts that have them (already so in the sidebar), and server search speaks IMAP `SEARCH` instead of Gmail's language (see Searching the server).
- **Servers that are label stores underneath** (Gmail over IMAP is the one people meet, and the first live test target) show every label as a folder and every message in `\All` ("[Gmail]/All Mail"). There `\All` takes the archive role (archiving is removing the inbox copy, which Gmail turns into removing the label), and the virtual `\Flagged` and `\Important` folders are not synced as labels: they only mirror the star and Gmail's importance, which the flags already carry. All Mail is synced (it is the archive, it keeps mail whatever labels go, and server search looks there) but is no label (`folders::holds_everything`): every message is in it, so it would be a chip on every conversation and an entry in every label list, menu and `label:` search, and Gmail shows it as none; the All mail view shows its mail. Its copies put no label on a message, and nothing here makes it one (renaming, or making a label of its name, is refused). A store where an earlier pass kept it as a label is put right by the next pass: the label goes from the account and from every message, while the folder, its place and its copies stay, so nothing is read again. Gmail files sent mail itself, so its Sent append is off. An address can be one account only: adding an address Postrinch already has as a Google account is refused with a sentence.
- **The `\Archive` folder** (or one called `Archive`) is where archiving moves mail. It is an ordinary label, so archived mail shows in All mail as in Gmail. An account with none gets one made the first time something is archived.

## A message's identity

Gmail names a message once for its life. IMAP names a copy by `(folder, UIDVALIDITY, UID)`, which changes on every move. Postrinch's message id must not change on a move, or the outbox could not re-apply changes over sync, an open message would vanish from the reader when archived, and rules would see moved mail as new.

- **The provider message id is derived from the `Message-ID` header**: `m` and the first 24 hex digits of SHA-256 of the account key and the header as written, less its angle brackets and surrounding space (`imap::message_id`). The brackets go because `References` and `In-Reply-To` name the same message that way, and threading must find it by them; case stays, as a `Message-ID`'s left part is case-sensitive. Copies in several folders are one message with several labels, as in Gmail: a message sent to oneself is in Sent and the inbox.
- **A message without a `Message-ID`** (rare: some automated mail) gets `u` and a hash of the folder's label id, its UIDVALIDITY and the UID, in that order (`imap::message_id_without_header`). It is the one case where a move looks like a delete and a new message; nothing is lost.
- **Where each copy is** lives in the store as an `ImapPlace` (account, folder label id, UIDVALIDITY, UID, message id, the copy's flags and MODSEQ), so a change finds the copies to act on, and sync finds what a folder no longer has.

## Threading

Gmail threads mail itself; for IMAP Postrinch does (DESIGN.md open question 4).

- A thread is named by its root: the thread of the nearest stored ancestor in `References` (from the last entry back) or `In-Reply-To`; failing that, the first `References` entry, then `In-Reply-To`, then the message's own `Message-ID`. The thread id is `t` and a hash of that root, so a reply that arrives before what it answers still lands in the right thread once the root arrives (the root's own id hashes to the same thread).
- A message already stored keeps its thread when seen again: its second copy (Sent and the inbox), or every copy after a folder's UIDVALIDITY changed, even if an ancestor was stored in between.
- Threads never merge. A message is threaded once, when first stored, so a reply that names only its parent in `In-Reply-To` (no `References`) and arrives before that parent stays in a thread of its own when the parent turns out to be a reply too.
- No subject-only threading: it joins unrelated "Invoice" mails, and Gmail stopped doing it too.
- A thread is per account, as in Gmail. In the combined inbox, two accounts' copies of one conversation are two rows.

## Sync

Per account, one IMAP connection does the passes and backfill, a second downloads what the person opens (so it never waits behind a pass), a server search takes a third when the person searches (see Searching the server), sending a fourth when there is outgoing mail, and IDLE another where the server offers it (below): well under Gmail's limit of about 15. Each is kept between calls while it answers a `NOOP`, and opened again when it does not (`ImapSync` in `postrinch-sync/src/imap/sync/`). Sync sends its folder commands itself and reads every response up to the tagged one, because async-imap drops unsolicited responses (QRESYNC's `VANISHED` among them) that do not fit its channel.

- **Folders first.** `LIST` (with `SPECIAL-USE` where offered) gives the folders; each becomes a label (`put_label`), but Gmail's All Mail, whose label a pass removes should an earlier one have kept it. `\Noselect` and `\NonExistent` folders are skipped, as are Gmail's virtual `\Flagged` and `\Important`. Names are decoded from modified UTF-7 (Postrinch's own decoder: the `utf7-imap` crate panics on a malformed name) and shown with `/` between levels whatever the server's delimiter. A role goes to the folder the person chose in the account's settings, else to the folder SPECIAL-USE marks, else to one with a provider's usual name, one folder per role; `\All` is the archive where no folder is `\Archive`. Names go back to the server as quoted strings when they are 7-bit, and as literals otherwise (`{n+}` with LITERAL+, or LITERAL- under 4 KB; else `{n}`, waiting for the server's `+`), as some servers list raw 8-bit names; a name the client no longer has exactly (imap-proto turns bytes that are not UTF-8 into U+FFFD) is skipped with a warning, and every other folder still syncs.
- **Renamed folders** keep their label id, places and state; only the label's name changes. A kept folder LIST no longer shows is matched to a new one by RFC 8474 `MAILBOXID` (OBJECTID; read from each `SELECT` and, for the new name, from `EXAMINE`), else by UIDVALIDITY when exactly one folder went and one came with it (servers keep UIDVALIDITY across a rename; a new folder gets a fresh one). Folders with different MAILBOXIDs are never joined, and an ambiguous UIDVALIDITY is left alone (`renames.rs`).
- **Removals wait for folders read whole, one folder at a time.** A folder is read whole in a pass when it was opened, the server refused none of the commands sent in it, and every message asked for by its headers was answered; the sync cursor keeps, per folder, the last pass that read it whole and how many passes in a row did not (`reads.rs`). A message that lost its last copy goes once every folder has been read whole in a pass after it became pending (see "A message whose last copy is gone"), so one folder that could not be read this time holds back only removals, never the reading of the others. A folder that is not read whole five passes in a row (one that always refuses `SELECT`, say) stops holding them back: mail moved into it is then taken for gone, and comes back by its headers once the folder can be read again. A folder LIST leaves out is gone when two passes' LISTs leave it out (servers drop folders from LIST under load or while another client renames them): its places, label and state go then, whether or not every folder could be opened, since only LIST says what folders there are. A folder left out once counts as not read whole. A folder LIST still gives under a label the pass no longer gives it (its role changed, so its label did: an ordinary folder the person made Sent takes `SENT`, and the folder that was Sent goes back to a label of its own) is not missing: its old label goes in the same pass (`pass::superseded`), so it never shows twice.
- **Each folder** keeps `ImapFolder` state: name on the server, delimiter, label id, role, UIDVALIDITY, UIDNEXT, HIGHESTMODSEQ. A folder the server refuses to `SELECT` is left for the next pass. A `NO` to a command in a folder ends only that command: what it did answer is applied, nothing is taken for gone from a listing that did not come, and the folder's position does not move, so the next pass reads the same changes again. Mail at or above that position which such a pass (or one cut short by a busy server) already stored is told from new mail by the places kept, as when a folder is read whole: only its flags are read again (`UID FETCH <first>:<last> (UID FLAGS MODSEQ)`), never its headers, so a big burst cut short goes on where it stopped and a refusal that lasts costs no more each pass; kept places there that the new-mail listing no longer names are gone.
  - **A server busy for one folder or for the account** (`imap::refusal::busy_after_sign_in`). A `NO` to a command in a folder (`SELECT`/`EXAMINE`, `UID SEARCH`, `UID FETCH`, `UID STORE` and the like) whose code is `[INUSE]` or `[UNAVAILABLE]` is that folder's: once signed in, the server answers them about what the command touched (Dovecot's `NO [INUSE] Mailbox is locked`, for a lock held or left stale; Gmail's `NO [UNAVAILABLE] Temporary System Error`). The folder stops where it is (`sync::folder_error::FolderError::Busy`), its position does not move, nothing counts against its messages, and it counts as a folder not read this pass (towards the five passes after which it no longer holds removals back); the pass goes on to the other folders. Stopping the pass for it would stop every pass at that folder for as long as the lock lasts: the folders after it never read, and nothing removed. Backfill and the rename check skip such a folder in the same way. Words naming a known temporary limit (`TEMPORARY_LIMITS`, under `[ALERT]`, no code, `[UNAVAILABLE]` or `[INUSE]`) are the account's: every phrase in that table is about the account or its connections (connection count, daily bandwidth, sign-in service), never a folder, and Gmail answers any command `NO [ALERT] Account exceeded command or bandwidth limits.` once the day's limit is reached. They stop the pass with `SyncError::Busy` (backoff and `SyncEvent::Busy`, below), as do a `BYE` and a busy answer at sign-in, keeping what the pass already stored. `[LIMIT]` is busy only at sign-in (Dovecot's connection limit): after it, RFC 5530 means a fixed implementation limit ("too many UIDs in one command") that waiting does not lift, so it is a refusal of that command, as any other `NO`.
  - **UIDVALIDITY changed** (or 0: first time, or reset): the folder is read again: `UID SEARCH ALL` lists every UID, their flags are read `UID FETCH <first>:<last> (UID FLAGS MODSEQ)` a thousand UIDs at a time and applied as each batch comes (so memory stays at four bytes a UID, not a whole folder's flags), and the copies not kept are fetched by `UID FETCH <set> (UID FLAGS MODSEQ RFC822.SIZE INTERNALDATE BODY.PEEK[HEADER])`, newest first, a hundred at a time; an interrupted read carries on with the UIDs still missing. The copies of the earlier UIDVALIDITY are forgotten only then, so a message still there keeps its body.
  - **New mail**: the UIDs from the UIDNEXT read last time (`UID FETCH <UIDNEXT>:* (UID)`), then their headers the same way. Headers first, bodies after: backfill downloads bodies (`BODY.PEEK[]`) newest first, twenty at a time, over the pass's connection, giving way between batches when the next pass is due (see Backfill gives way, below). Unlike Gmail's first sync, nothing is downloaded whole during the pass; the reader's connection downloads what the person opens at once.
  - **Changed flags**: with CONDSTORE, `UID FETCH 1:<known> (UID FLAGS MODSEQ) (CHANGEDSINCE <modseq> VANISHED)`, skipped when HIGHESTMODSEQ has not moved; without it, `UID SEARCH UID 1:<known>` and then `UID FETCH <first>:<last> (UID FLAGS)` a thousand UIDs at a time.
  - **Gone mail**: with QRESYNC (`ENABLE QRESYNC` once per connection), the `VANISHED (EARLIER)` of the same fetch; with CONDSTORE alone, `UID SEARCH UID 1:<known>` compared with the places known; without CONDSTORE the same `UID SEARCH`.
  - **A message whose last copy is gone** loses its labels at once and is kept as pending in the account's sync cursor (written before its places go); the cursor notes the pass it became pending in, and it is removed at the end of a pass once every folder has been read whole since, if it still has no copy. So mail another client moved from one folder to another keeps its body, even when the move happened mid-pass into a folder already read, or the destination could not be opened, and an interrupted pass leaves nothing behind (`pending.rs`).
  - **A message the server lists but gives no headers for** (Gmail ends such a FETCH `NO Some messages could not be FETCHed`, Dovecot `NO [SERVERBUG]`) does not stop the folder or the pass: the answers that came are stored, and the UIDs that did not are kept per folder in the sync cursor with a count of passes. The folder's UIDNEXT and HIGHESTMODSEQ move on as usual, so no range of UIDs is left unchecked for expunges; the owed UIDs are asked for again by UID (after a `UID SEARCH` confirms they are still there) until they answer. After three passes without an answer one is stored as mail that cannot be read (below), so a message that never answers cannot hold the folder unread for ever, and the list stays small. A `NO` that says the server is busy (above) is not a partial answer: it stops the folder or the pass, and nothing counts against the messages.
  - **FETCH answers** are merged by UID within a command: a server may split one message's items over several responses (RFC 3501 7.4.2), and a response without a UID is matched by its sequence number (kept current through `EXPUNGE` and through a `VANISHED` without `EARLIER`, which is an expunge too: a message's number drops by the vanished UIDs below its own). `VANISHED` is kept as UID ranges, so a folder emptied of a million messages costs a few ranges. Only UIDs in the requested set are answers; a message is counted as answered for headers only when its header came. A response without FLAGS leaves the copy's flags as they were, rather than clearing them. Unsolicited flag updates (CONDSTORE servers send them for other messages mid-command) are dropped: the pass keeps the HIGHESTMODSEQ read at `SELECT`, so the next `CHANGEDSINCE` (or, without CONDSTORE, the next full flag listing) reads them again (`fetch.rs`).
  - **Several copies of one message** (one `Message-ID` in several folders): one copy gives the message its date, headers and body: the one with the earliest INTERNALDATE (kept on each place as `arrived`), copies without one last, then the lowest folder label id, then the lowest UID (`places::first_copy`). So the choice is the same whatever order folders and passes read the copies in, and backfill downloads the body of the copy the headers came from.
  - **Mail that cannot be read** never stops a pass: errors name the folder and UID. A copy whose headers cannot be parsed (a zero-byte message, as maildir servers can hold, or garbage) is stored minimally: an id from its folder, UIDVALIDITY and UID (as for mail without a `Message-ID`), its INTERNALDATE, size and flags, and an empty subject. A body that cannot be parsed is stored as downloaded, with the raw bytes and what the headers gave. So backfill asks for it once and not on every pass, and the person still sees the message and can save it; dropping it would hide mail that is on the server, and retrying it would cost a download each pass for a message that will never parse.
  - Folders are synced inbox first, then Sent, Drafts, user folders, Archive, Trash and Junk; the position is written per folder only after what came before it is stored, so an interrupted pass repeats work and never skips mail.
- **Flags**: `\Seen` ↔ read, `\Flagged` ↔ starred, and a copy marked `\Deleted` counts as gone. A message is unread if any copy lacks `\Seen` and starred if any has `\Flagged`. `\Draft` and keywords are kept on the copy (`ImapPlace::flags`); a draft is what the Drafts folder holds (its `DRAFT` label), as for Gmail.
- **New mail at once: IDLE on the inbox** (RFC 2177; `imap/sync/idle.rs` and `idle_wire.rs` for the connection, `mail/imap_idle.rs` for its loop). Each IMAP account whose server offers IDLE keeps one more connection, beside the sync connection, that `EXAMINE`s the inbox (the folder kept with the inbox's role, else `INBOX`) and IDLEs. It never syncs: news in the inbox (`EXISTS`, `EXPUNGE`, `VANISHED`, `FETCH`) ends the IDLE a moment later (`IdleOptions::settle`, 1 second, so a burst wakes one pass) and wakes the account's sync loop, which runs a pass on its own connection. The IDLE is ended and begun again on the same connection every 25 minutes (`IdleOptions::restart`; RFC 2177 lets a server drop one after 29). What is sent before the server's `+` and after `DONE` is under the command timeout; silence while idling is not. It runs in the account's keep-in-sync task beside the sync loop, so it starts and ends with it (the account removed, or needing to sign in), and connects first after a pass that worked, so the inbox is known and the sign-in has just worked. When the account's connections are let go (`ImapSync::disconnect`: signing in again, new servers, the account added again or removed), it ends its IDLE with `DONE`, signs out, and waits for the next pass that works, so it signs in with the new secret, at the new servers; an OAuth account's access token comes from the same token slot as every connection's, refreshed when about to expire. A lost connection, a `BYE` or a timeout wakes a pass (news may have been missed) when an IDLE had begun, and connects again after a backoff (`IdleOptions::reconnect`, from about 30 seconds doubling to 15 minutes) that an IDLE ending well resets. So does a server that ends each IDLE itself as soon as it is asked (within a second, before or after its `+`), which would otherwise have IDLE sent again and again without a pause. A connection's first IDLE wakes a pass when the connection was made again without waiting for one (after a lost connection), or while a pass is under way: the last pass, or that one, may have read the inbox before the new `EXAMINE`, and mail delivered in between is in the `EXAMINE`'s count but never told of by an IDLE, so it would otherwise wait for the 5-minute poll. A busy server is the account's: the IDLE waits out the busy gate the other loops share, and a busy answer of its own (a `BYE` or `NO` in busy words, or at sign-in) takes the gate's next wait and sends `SyncEvent::Busy`, never "needs to sign in". A refused sign-in on the IDLE connection is left to the pass, which records it and asks the person as for any refused sign-in: the IDLE wakes a pass and tries again only after the next one that works. When the server says the account has too many connections (`[LIMIT]` at sign-in, or a connection limit's words: `refusal::names_connections`, carried as `SyncError::Busy { connections: true }`), the IDLE connection is the one that gives way: it stays away for 30 minutes (`IdleOptions::give_way`) while the account is polled. That holds whichever connection is refused. Refused itself, the IDLE connection stays away, and the other connections and the busy gate are left alone. When another of the account's connections (passes, reads, outgoing mail) is refused so while the IDLE connection is signed in, or still signing in or `EXAMINE`ing the inbox (the server may count it from the moment it accepts the sign-in, so it is held from before it signs in), that connection asks the IDLE to give way (`imap/sync/idle_link.rs`), waits for it to end its IDLE, or to finish being made without beginning one, and sign out, and signs in again at once in its place, with no busy wait shown; only when it is refused again, or no IDLE connection was there to give way, is the refusal the busy gate's. A pass is woken once the IDLE has gone, as for a lost IDLE, when an IDLE had begun. A server that does not offer IDLE once signed in is polled only, and asked again only when the account's connections are let go.
- **Polling.** Every account is polled as well, IDLE or not: every minute (`KeepOptions::interval`) without an IDLE begun, every 5 minutes (`IdleOptions::interval`) while one watches the inbox. The inbox's news comes at once then, so passes are for the other folders (mail a server's own filters put there, Sent and Drafts from other devices, flags changed elsewhere); five minutes keeps them reasonably fresh while cutting a busy account's passes, and the bandwidth and command counts some providers limit, by four fifths. An IDLE that is lost wakes a pass, after which passes come every minute again until one is begun.
- **Backfill gives way** (`postrinch-sync/src/giving_way.rs`). A pass is a sync, then backfill, and backfill on a new account runs for most of an hour (6,500 messages at twenty a batch). Everything that asks for a pass would wait behind it: a send (the app wakes a pass on `SyncEvent::Sent` to bring in the server's copy in Sent), Sync now, an IDLE's news, the poll. So backfill stops between two batches once the next pass is due: the loop was woken, or the poll interval (the one the pass would pause for: a minute, or five while an IDLE watches the inbox) has gone by since backfill began. The interval counts from backfill, not from the pass, so a sync as long as the interval (a slow server, a big burst of new mail) still leaves backfill a whole interval, rather than one batch per pass with a new sync at once. It always does one batch first, so it gets on however often passes come, and never stops after its last, so one that finished says so. A backfill that gave way to a wake is owed its share in the next pass (`giving_way::Share`): a wake then stops it only once it has run as long as that pass's sync took, so wakes that keep coming (a busy inbox's IDLE news, sends one after another) leave it at least half the account's time, while a lone wake (Sync now) is answered at the next batch. The loop then runs the next pass at once, and that pass's backfill carries on from the newest message still left, which puts the bodies of mail the pass just found first. A wake is taken when backfill gives way to it (one that comes while backfill is owed time is left for later), and one that comes after backfill gave way and before the next pass begins is taken by that pass: each wake brings one pass, never none and never two. A pass whose backfill took a wake is followed by the next at once however it ended, a failure after it included (the failure is reported as ever, and its retry wait skipped), since the wake that would end that wait is used up. A pass whose backfill gave way sends no `SyncEvent::Done` (its account is not up to date yet); the next pass's `Started` and `Synced` show between, and the bodies' count goes on where it was, with what the pass between added in its total: "Downloading older mail: 2,920 of 6,498", then "2,940 of 6,499", never back to nothing (`giving_way::Tally`); a backfill that failed partway carries its count on the same way. A sync that read the account or a folder whole (the account added again, a folder's UIDVALIDITY new) starts the count again. Gmail's loop does the same for Google accounts, once for the whole pass over them: it syncs every account first and then backfills each, so the pass a wake asks for reaches every account's new mail without waiting behind another's backfill; once one account's backfill gives way, it starts no more downloads (those under way are seen through), the accounts after it do at most one round of downloads, and the next pass begins at once.
- **An opened message not downloaded yet** is fetched at once (`BODY.PEEK[]` from its first copy, as above), as for Gmail.
- **A busy server** (`SyncError::Busy`, see Credentials: too many connections, a bandwidth limit, a sign-in service down) is to be waited out, never shown as "needs to sign in". What exists now: the classification (`ImapSession::open`, `list_folders` and `SmtpConnection::open` return `SyncError::Busy`, including for a `BAD` naming a known limit (`imap::refusal::is_temporary_limit`) to the CAPABILITY or LIST that follows a sign-in, as Microsoft 365 sends "User is authenticated but not connected" there, for a `BYE` greeting at a limit, and for a `NO` naming an account-wide limit to any command a pass sends; a `NO [INUSE]` or `[UNAVAILABLE]` in one folder stops only that folder, see Sync), the account check's `CheckFailure::Busy`, `Backoff` (`postrinch-sync/src/backoff.rs`: from about 30 seconds, doubling with jitter, capped at 15 minutes) and `SyncEvent::Busy { account, message, retry_in }`, which the window shows as "Server busy; trying again in …" without touching the account's sign-in state. The keep-in-sync and sending loops (`postrinch-sync/src/mail/imap_keep.rs`) keep one `Backoff` per account and server (IMAP and SMTP, shared by both loops), take the next wait from it on each `Busy`, reset it on the next pass that signs in, and send `SyncEvent::Busy` with the server's sentence and that wait; a wake (Sync now, a change made here) does not cut a busy wait short, only makes the loop look at it again. The waits are the IMAP engine's (`ImapSync`, `imap/busy.rs`), so removing an account, or adding it again (its servers just checked, perhaps new ones), forgets both its servers' waits: the next wake finds the account gone, or nothing to wait out, and a removed and re-added or moved account never waits out its old server's back-off. Other failures keep the ordinary retry and `SyncEvent::Failed`.

## Changing mail

The outbox stays as it is: a `MessageChange` per set of messages, applied here at once, sent in order, applied again over whatever sync brings back until a later sync has it. IMAP's sender turns each change into commands per message, from its places:

| Change | IMAP |
|---|---|
| read / unread | `UID STORE ±FLAGS.SILENT (\Seen)` on every copy |
| star / unstar | `UID STORE ±FLAGS.SILENT (\Flagged)` on every copy |
| add a label (a folder) | `UID COPY` one copy into it |
| remove a label, others remain | delete that copy, once another is seen on the server: `\Deleted` then `UID EXPUNGE` (UIDPLUS) |
| remove `INBOX` with nothing added (archive) | `UID MOVE` the inbox copy to the archive folder |
| remove one folder, add another (move) | `UID MOVE` |
| add `TRASH` | `UID MOVE` one copy to Trash, delete the others (Gmail drops a trashed message's other labels too) |
| remove `TRASH` (restore) | `UID MOVE` back to the inbox, or the folders the change adds |
| add/remove `SPAM` | as for Trash, with Junk |

- Without `MOVE` (RFC 6851), a move is `UID COPY` and then a delete of the source: `\Deleted` and `UID EXPUNGE`, or without UIDPLUS a plain `EXPUNGE` (see "Keeping every message safe" for when each may go).
- The places a command makes are recorded at once (from UIDPLUS's `COPYUID`, or found among the destination's new mail by `Message-ID`), so the next sync reads only their flags.
- Removing a message's last folder never deletes it: it moves to the archive (one named `Archive` is made where there is none), or, from Trash or Junk, to the inbox. Gmail's All Mail (`\All` where the server offers Gmail's `X-GM-EXT-1`) holds every message: it is never deleted or moved from, except into Trash or Junk, and there archiving deletes only the inbox copy. Elsewhere a `\All` folder (Dovecot's `virtual/All` and the like) is a view of the other folders, whose "copies" are their messages: it is not synced and never counts as keeping a message, so archiving there moves the inbox copy to a real archive folder (`\Archive`, one named `Archive`, or one made). Nor is mail filed in one: a change adding the label of a folder that has become a view since sync kept it is refused, with that reason.
- A copy is deleted only once the server has confirmed, in the same run, another copy that keeps the message; copies are moved and copied only from copies the server is seen to have (see "Keeping every message safe").
- Changes go over the connection passes use, so a change and a pass never cross in one folder. Runs of the same change go together, up to 1000 messages, 500 UIDs to a command.
- **Refused for good** (a `NO` with `TRYCREATE`, `NONEXISTENT`, `NOPERM`, `CANNOT`, `READ-ONLY`, `ALREADYEXISTS`, `LIMIT`, `OVERQUOTA` and the like): dropped with its reason and the messages shown as their copies are, as Gmail's 400/404. Busy (`INUSE`, `UNAVAILABLE`) or out of reach, or waiting for something that comes in time (sync to read a folder whose UIDVALIDITY changed, other mail marked deleted to go, a copy not made to be made again): tried again however long it takes, and never counted. Busy or out of reach holds the whole outbox back, as nothing would go; a change that waits for something holds back only the later changes to its messages, so each message's changes keep their order and the rest of the outbox goes on. Any other `NO` or `BAD`: tried again, and dropped after 5 such sends of that entry, so one change cannot hold the outbox back for ever. In a run that fails so, each change is sent alone, so only the one refused is dropped.
- **Labels**: making one is `CREATE` (one there already will do) and `SUBSCRIBE`; renaming is `RENAME`, the folders under it following, the label keeping its id. A label with `/` in its name is a nested folder, each level in modified UTF-7 and joined by the server's delimiter, under `INBOX` where the server keeps every folder there (Courier, or a personal namespace of `INBOX.`). RFC 2342's `NAMESPACE` would say so, but imap-proto, the parser sync uses, cannot read its answer, and an answer it cannot read stops the connection; so the folders are the evidence: every folder beside the inbox under it, the special folders among them. The person's own folders under the inbox prove nothing (an account elsewhere may keep them there), and an account with no special folder yet gets its labels at the top. The special folders, and a view of all mail, are not renamed or deleted.
- **Deleting a label** is `DELETE`, which deletes the folder's mail, so the mail is saved first from what the server has, not what the store knows (a first read or backfill still running, owed headers, mail just arrived): `UID SEARCH UNDELETED` lists the folder at its UIDVALIDITY now, and every message there is copied to the archive (made where there is none), except one with another copy the server is seen to have now. Mail the store does not know is read first (its headers, as sync reads new mail, after checking the folder's UIDVALIDITY is still the one listed), so its copies are kept as any change's are, and a deletion tried again after a failure copies nothing twice. The folder is listed again after the copies, and whatever came in copied too, until a listing finds nothing new (five at most; then it waits). Where the account is Gmail, All Mail keeps the mail and nothing is copied. Each listing opens the folder afresh, and should its UIDVALIDITY differ from the first listing's (another client deleted and made it again meanwhile), the UIDs seen name other mail, so the deletion waits for sync to read it. Should anything not be saved for sure (a folder changed, a listing refused, a copy refused or not confirmed), the folder is not deleted. A folder with folders under it (in `LIST`) is not deleted either, saying which: some servers delete them with it, and each is a label of its own, as renaming moves them with it. Mail another client marked `\Deleted` there goes with the folder, as that client's expunge would take it; mail arriving between the last listing and the `DELETE` is lost with it, as IMAP cannot delete a folder only if nothing came in.

### Keeping every message safe

A change that moves or deletes copies could lose mail if it trusted the store: the store's copies are what the last sync read, another client may have expunged one since, and a `UID COPY` or `UID MOVE` of a UID that is gone answers `OK` and does nothing. So changes keep one rule: **nothing is deleted or expunged on a guess.** When in doubt the mail stays: a duplicate is harmless, a loss is not.

- **Confirmed and guessed.** A copy is *confirmed* when the server has said so in this run: `UID SEARCH UID <uids> UNDELETED` in its folder, at the folder's UIDVALIDITY now, found it; or `COPYUID` (UIDPLUS) named the UID a command gave it; or a listing of the destination's new mail (`UID FETCH <UIDNEXT before>:*` with headers) found it by `Message-ID`. Copies confirmed by a command or a listing are recorded as places at once. Anything else is a guess: a copy sync read earlier and not searched for in this run, a copy in a folder whose UIDVALIDITY changed, a command that answered `OK` without saying where it put the copy. A guess is acted on only where that cannot lose mail: its flags set, or a copy made from it whose result is then confirmed or not.
- **Sources are searched for first.** Before a change copies, moves or deletes anything of a message, every copy of it kept is searched for (one search per folder for all the change's messages). Copies found gone are forgotten and the message's change planned again from the rest, so labels are added and mail moved from a copy that is there; when none is left, there is nothing to change.
- **When a delete runs.** A copy is deleted (`\Deleted` and an expunge; a move without `MOVE` is a copy and then this) only when its message has another copy, confirmed in this run, that the change leaves in place: one the search found and no op of the change moves or deletes, or one a copy or move of this change made. A message whose change only deletes and that keeps no confirmed copy has one copy moved where a message in no folder goes (the archive; from Trash or Junk, the inbox) instead, but only when the search answered and found every other copy gone; a search the server refused says nothing either way, so the deletes do not run and the change waits. Otherwise its deletes do not run, and the change waits, is tried again or is refused (below), planned afresh from what the server then has.
- **Searched again just before the deletes.** The copy that keeps a message is searched for once more just before each folder's deletes, as another client may have deleted it since the first search; one gone (or not answered for) holds those deletes back, and the change waits. That shrinks, and cannot close, a race between two clients: each may confirm the other's copy, then delete its own, in the moment between the last search and the expunge. IMAP has no way to delete one copy only if another still exists. The window is one round trip per folder, and it needs another client deleting the very copy this change counts on at that moment.
- **Folders that are views.** A folder is taken as holding real copies unless the server marks it `\All` (and it is not Gmail's): a virtual folder the server does not mark so (a Dovecot virtual mailbox of another kind, say) counts as a real copy and can keep a message whose other copies are then deleted. IMAP gives no general way to tell a view from a folder; a server that offers views should mark them.
- **Copies whose UID is not said.** Before each `UID COPY` or `UID MOVE`, the destination's UIDVALIDITY and UIDNEXT are read (`STATUS`), and an attempt is written for each message (`ImapCopyAttempt`: folder, message, that UIDVALIDITY and UIDNEXT). An attempt is never a copy: it never keeps a message and never lets a delete run; it only stops a copy being made twice. After the command each message's copy is *confirmed* (its attempt goes), *not made* (the listing answered in full and the message is not there: its source went between the search and the command; the attempt goes and the change waits, to be planned again from a copy that is there), or *not known* (its new mail could not be listed: tried again and counted towards giving up; or the folder's UIDVALIDITY changed meanwhile: it waits), when the attempt stays.
- **Retries avoid duplicates.** A change sent again first settles its messages' attempts with a live listing of each destination from the attempt's UIDNEXT: found (an answer lost with the connection, a listing refused) means the copy is there, recorded and not made again; not there means it never was, and the attempt goes. An attempt also goes once sync has stored its message's copy in that folder, and with the folder. A folder whose UIDVALIDITY changed since is read whole by sync, so its attempts go and the copy may be made again: a duplicate, never a loss. A message without a `Message-ID` cannot be found by one, so without UIDPLUS its attempt stays until sync has read the folder past the attempt's UIDNEXT (at the same UIDVALIDITY, with no mail there still owed its headers), when the copy, if made, is stored as a message of its own; until then it is copied there at most once, and a move to the archive or the bin that would make that copy again is refused, saying why. A change that would delete its other copies on the strength of that copy is refused with that reason, and the message stays in both folders. A folder the server will not open when its attempts are settled holds no copy (deleted there since sync read it): its attempts go. At the end of each sync pass, attempts nothing would settle go: those sync has read past, and those of a message with no copy left that sync knows of, from which no copy could be made again.
- **Waits are bounded.** Each wait ends on something that comes: a busy server (backoff), a folder whose UIDVALIDITY changed (sync's next read of it), another client's mail marked `\Deleted` (until a sync has seen it marked, below), a copy not made or not known (the next send settles it with a live listing), a search the server would not answer (the next send asks again). That last is the one wait nothing bounds: a server that never answers the search for a folder leaves the change's other ops done and its deletes undone, the copies in place, as nothing else can show they may go. Nothing waits for sync to read past a guess. A refusal that is not for good counts towards giving up (5 sends); a wait never counts. Deleting a label never waits on mail whose headers the server will not give (below).
- **Our marks are noted before they are made.** Every `\Deleted` Postrinch sets, by a change or by replacing or sending a draft, is noted in the sync cursor (per folder: its UIDVALIDITY and the UIDs) before the `UID STORE`, and again once the server has taken it; a UID goes from the note once expunged, unmarked again, or found no longer marked. So a mark stranded before its expunge (a connection lost, a busy answer, a crash) is still known as ours: it never passes for another client's mail marked mid-delete, and each send of the outbox first expunges the marks left in each folder (`UID EXPUNGE` of just those with UIDPLUS; without it a plain `EXPUNGE` only where nothing else is marked). The cursor is read, changed and written as one step under a lock, so the outbox and outgoing mail never lose each other's notes.
- **The expunge fallback, without UIDPLUS.** A plain `EXPUNGE` removes every message marked `\Deleted` in the folder. So each folder a change deletes from is checked with `UID SEARCH DELETED` before anything is copied, and again once ours are marked, just before the `EXPUNGE`; the `EXPUNGE` goes only when the marked mail is all ours: the copies deleted now and those this account left marked there before, as noted above. Other mail marked there may be another client's mid-delete: the change waits for it (and our mark comes off again), until a sync has seen that mail marked (ours are never among it, being noted before they are made). Then that client is one that leaves mail marked and never expunges (Thunderbird's "mark as deleted"), which would hold the change for ever: ours are marked, left unexpunged and noted as ours, and the change is done, as a copy marked `\Deleted` counts as gone, as sync has it. The next delete in that folder once that other mail is gone expunges ours left there too, so they never pile up; noted UIDs no longer marked are dropped at each check. Mail another client marks between the last check and the `EXPUNGE` is expunged with ours: plain IMAP cannot expunge only some messages; the window is one round trip, and that mail was marked to be expunged.
- **Deleting a label** saves what is only in the folder by the same rules: another copy keeps a message only when the search finds it there now, never an attempt, and the folder is deleted only once every copy to the archive is confirmed. A message whose headers the server will not give (corrupt mail) is not waited for: it is copied by its UID, no headers needed, and with UIDPLUS its `COPYUID` confirms it (sync reads the archive's copy as new mail; a deletion tried again may copy it twice). Without UIDPLUS nothing can confirm that copy, so the deletion is refused, saying why, and the folder and its mail stay.

## Writing and sending

- **Sending is SMTP** (`lettre`): submission on 587 with STARTTLS or 465 with TLS, authenticated as the account. The queue (`Outgoing`) and its order, refusals and retries stay as they are.
- **Each message goes once.** SMTP gives no way to ask whether a message got through, so the risk is narrowed: a reply of 4xx before the data is accepted means it did not go and is retried; a 5xx means refused, and waits for the person; a connection lost after the data was sent is the one uncertain case: Postrinch looks for the message's `Message-ID` in Sent (a provider that files sent mail itself shows it there), and when it isn't there the mail waits for the person, saying it may have gone, with Send again and Discard. It is never retried blind.
- **Sent**: after a send, the message is `APPEND`ed to Sent (`\Seen`), unless the account's settings say the provider files sent mail itself (Gmail-like servers, Outlook, iCloud: a setting, on by default, turned off when Sent has not held the message a moment later for three sends in a row, and back on when the provider is seen to file it after all, once a back-off has passed). The place is recorded from APPENDUID.
- **Drafts live in the Drafts folder.** Keep as draft `APPEND`s the message (`\Draft \Seen`); keeping it again appends the new one and deletes the old; sending deletes it.
- Replies thread by `In-Reply-To` and `References`, which compose already writes.

How it is built (`postrinch-sync/src/imap/sync/send/`, called as `ImapSync::send_outgoing`):

- **How far a send got is kept with the message** (`Outgoing.stage`, a `SendStage`): `DataSent` is recorded just before the data goes, `Delivered` once the server took it. A message whose data was written in full without an answer (the connection lost, or the app stopped) is `DataSent`, and the next attempt looks in Sent instead of sending; one written only in part did not go and is sent again. A `Delivered` message is only filed and its draft deleted: it is never sent twice. Recording that the server took a transaction is tried again (after 100 and 500 ms) before giving up; if it still fails, the message stays `DataSent` and waits for the person, saying whom it went to, that Postrinch could not record it, and that Send again would send it to them a second time. Send again (`Store::outgoing_send_again`) queues a may-have-gone message as new, and leaves a delivered one delivered.
- **The envelope**: MAIL FROM the account, RCPT TO each recipient once (To, Cc and Bcc). Any recipient refused (5xx) refuses the transaction, naming the address, so a transaction never goes to some of its recipients only. The copy sent has no `Bcc` header; the copies in Sent and Drafts keep it. Non-ASCII addresses need SMTPUTF8 and 8-bit messages need 8BITMIME, or the message is refused.
- **A server that takes only so many recipients at once** answers a RCPT beyond them "too many recipients": the enhanced code X.5.3 (`452 4.5.3`, `552 5.5.3`), or a 452 or 552 without an enhanced code once some recipients were taken in the transaction (RFC 5321 4.5.3.1.10 allows 552 for it). A 452 with another enhanced code is about that recipient (`4.2.2`, the mailbox full, as Gmail answers; `4.3.1`, the server out of storage), and a 552 that is not "too many" refuses the message. As RFC 5321 4.5.3.1.10 says, the message then goes to those it took, and to the rest in further transactions on the same connection, so it reaches each recipient once (`submit.rs`, `transmit.rs`). Whom each transaction went to is recorded before the next begins (`Outgoing.delivered_to`, with the transaction in flight as `Outgoing.sending_to` while it is `DataSent`), so no attempt, and no Send again, sends it to them a second time. "Too many" to the very first recipient is the server busy (a 4xx, retried later) or a refusal (a 5xx). A recipient refused in a later part refuses the rest, saying whom it went to. A later part lost after its data is not looked for in Sent, which holds the message from the earlier parts whatever became of this one: it waits for the person, saying whom it went to and whom it may have reached. A provider that files sent mail may file the message once per part.
- **A recipient the server puts off** (any 4xx at RCPT for them alone but "too many" and 421, which closes the connection) is left out of the transaction, which goes on for the others: they have it at once, and it is filed in Sent once everyone has (`submit.rs`, `put_off.rs`). With nobody taken, no data is sent. How often and since when each was put off is kept with the message (`Outgoing.put_off`, `Store::outgoing_put_off`), and the attempt ends as the server busy (`SyncError::Busy`, naming the recipient and the server's words), after the account's other waiting mail, which it does not hold up. The next attempt sends to them only. Once a recipient has been put off on six attempts (`PUT_OFF_ATTEMPTS`) or for a day (`PUT_OFF_FOR`), the message waits for the person instead, saying whom it went to, whom the server put off and in what words; Send again forgets the count. Whom it went to is recorded as for parts, so nobody gets it twice.
- **Looking in Sent** is `UID SEARCH HEADER Message-ID`, the folder opened again (EXAMINE) each time. For a provider that files sent mail it looks at once and then after a few waits (`SentLookup`, by default 1, 2, 4 and 8 seconds); otherwise once. When the provider said to file it has not after those waits, Postrinch appends the copy and counts a miss; the account's setting goes off only after three misses in a row (`SENT_MISSES_ALLOWED`), since Exchange or iCloud can take longer than the waits now and then, and a copy found sets the count back to none. A provider whose setting is off that files sent mail all the same shows it: the message Postrinch last filed itself has two live copies in Sent (under the folder's UIDVALIDITY now, as the send's EXAMINE gives it) once sync has read them, and the next send turns the setting back on before it files (`Store::server_files_sent`). A provider that files only after the waits shows two copies too, but of the copy Postrinch filed after a miss: that is not a copy found in time, so the misses go on counting and the setting still goes off after three. So that such a provider does not flip the setting back and forth, once Postrinch has turned it off a second copy turns it back on only after a back-off since it went off (`SentLookup.back_off`, a `SentBackOff`): an hour the first time, doubling each time it goes off again (two hours, four, and so on), at most a week. A copy found within the waits starts the back-off again from an hour. So a provider that was only slow for a while (an outage) gets its setting back, and the duplicates stop, within the hour; one that always files late gets the waits back at most once a week, for three sends. A setting the person turned off (no back-off) comes back at the first second copy, and a clock set back starts the wait again from then, so no state is kept for good. The duplicate copy is left in Sent; it is one message in Postrinch, with two places. The count, that last message, how many times the setting went off since a copy was found in time and when it last did are kept on the account (`Account.sent_filing`; the `late` and `after_miss` fields earlier versions kept are no longer read), and each change reads the account and writes back only that setting and that state, under the store's account lock (`sent_filing.rs`), so settings saved during a send are never reverted.
- **A delivered message whose Sent refuses the copy** (over quota, say) waits for the person, saying so, but its draft is deleted all the same: the message went. Send again only files it.
- **A delivered message whose attachment has gone** from this computer is filed in Sent without it (logged), rather than waiting for ever on bytes that are not coming back. A message not yet sent, or a draft to keep, whose attachment has gone is refused, naming it: the person takes it out or attaches it again.
- **Sent and Drafts** are the folders the store has for those roles, else the ones LIST gives, by the same rules sync gives folders their roles. With no Drafts folder, keeping a draft is refused; with no Sent folder, a sent message is not filed (logged). A Sent or Drafts folder the store has that was deleted on the server since is one the server will not open (a `NO` to EXAMINE): it holds nothing to find or count, and the APPEND's refusal makes that message wait for the person while the rest of the account's outgoing mail goes on. A busy answer to the EXAMINE is the server busy, as anywhere.
- **Drafts are kept once**: an attempt first looks in Drafts for the draft's own `Message-ID`, so one that an earlier attempt appended is not appended again. The old draft's copies are found by the places the store keeps and by its `Message-ID`, marked `\Deleted` and expunged: by `UID EXPUNGE` with UIDPLUS; without it, by `EXPUNGE` only when no other message in the folder is `\Deleted`, otherwise left marked, which Postrinch counts as gone. A draft with no live copy left is pending, as one sync saw go is, and leaves the store at the end of a later pass.
- **Without UIDPLUS, `EXPUNGE` has a race no client can close**: between the `UID SEARCH DELETED` that finds no one else's marked message and the `EXPUNGE`, another client may mark one, and the `EXPUNGE` takes it too. That client meant it to go, and most clients expunge what they mark themselves soon after, so the harm is that it goes a little sooner than its owner would have expunged it. Servers without UIDPLUS are rare.
- **What a draft replaces is the copy on the server.** A Keep the server refused never got there, so a later Keep or Send that replaces it deletes what that Keep would have replaced, and so on back, and the refused Keep, now out of date, is done with (`drafts.rs`, `Replaced`), whether or not there is a Drafts folder to delete from (a Keep refused for want of one, then sent, is done with too). The `Message-ID` a queued draft goes out with is `outgoing_message_id`, so the window can name what it last kept.
- **Places**: with UIDPLUS, an appended copy's place is recorded from APPENDUID (when the store keeps that folder), and sync fetches the message itself; without it, both are left to sync. Either way the message is stored once.
- Sending uses its own IMAP connection (`Lane::Outgoing`), so it does not wait behind a sync, and one SMTP connection per attempt at a message.
- **One delivery per account at a time**: `send_outgoing` holds the account's sending lock while it works, so two callers (the app's sender and a "send now", say) never read the same message waiting and send it twice; the second waits, then finds what is left.

## Credentials

- **OAuth first, passwords only where there is no OAuth.** As DESIGN.md says, app passwords are a fallback, never the main path: they are long-lived, see the whole account, and are typed by hand. Wherever Postrinch has an OAuth client for the provider, the add-account dialog's way in is "Sign in with <provider>" in the browser, and it is the only way in: both providers that have one take no passwords from Postrinch. Google over IMAP signs in only in the browser because Google no longer reliably offers app passwords (its app-password page is often missing), so discovery marks Google's mail OAuth 2 only with no app-password page (`Discovery::oauth2_only`, set for `HostedBy::Google` whichever step answered), and neither the dialog, the Thunderbird import nor `postrinch-cli add-imap` asks Google's mail for a password; without Google's sign-in over IMAP in this copy, Google's mail is offered only as a Google account. A password is the first choice only for providers that offer no OAuth to apps like Postrinch (iCloud; Fastmail, which keeps OAuth for partners; most work and self-hosted servers).
- **Providers with OAuth in this release:** Google over IMAP (the existing Google client: its `https://mail.google.com/` scope covers IMAP and SMTP, so nothing new is registered), and Microsoft (Outlook.com, Hotmail, Live and Microsoft 365: password sign-in is gone there, so OAuth is the only way; a public "Mobile and desktop" client registered in Microsoft Entra, redirect `http://localhost`, delegated `IMAP.AccessAsUser.All`, `SMTP.Send`, `offline_access`, `openid`, `email`; its client id in `~/.config/postrinch/microsoft-oauth-client.json`, kept out of git like Google's). Yahoo and AOL follow once Yahoo approves a developer app for mail; until then they use app passwords. An organization whose admin requires consent for apps shows that as the account's sign-in trouble, in the admin's words.
- **Passwords and app passwords**: kept in the keychain under the service `postrinch.imap`, keyed by the account's address, as JSON (`{"kind":"password","password":…}`), never in the store. One secret for IMAP and SMTP unless the person gives SMTP its own, which is kept in the same JSON as `"smtp_password":…` (`ImapSecret`, `ImapSecrets` in `postrinch-sync/src/imap/secret.rs`). The keychain code is shared with Google's (`postrinch-sync/src/secrets.rs`, `Keychain::GOOGLE` and `Keychain::IMAP`).
- **OAuth 2 (`XOAUTH2`/`OAUTHBEARER`)** for providers that require it: the same loopback flow as Google's, with the provider's endpoints and client id, its refresh token kept as `{"kind":"oauth2","provider":…,"refresh_token":…}`, and access tokens refreshed before they expire and once more on a refused AUTHENTICATE. Signing in takes its access tokens from an `AccessTokens` (`postrinch-sync/src/imap/tokens.rs`: `access_token` and `invalidate`), which the provider's flow implements; XOAUTH2 is used where offered, OAUTHBEARER (RFC 7628) where it is all the server offers. The flow and SASL are built generically; adding a provider is its endpoints, scopes and client id. Which provider an account uses is found from discovery, never asked.
- **How the OAuth flow is built** (`postrinch-sync/src/oauth/`, shared with Google accounts): PKCE, the loopback redirect, the code exchange, refresh and revocation, described per provider by an `OAuthSpec` (endpoints, client id and optional secret, scopes and the ones a grant is refused without, how the redirect names this machine, how the signed-in address is learnt, what token errors mean). Google accounts' and Google over IMAP's specs are in `google/oauth.rs`, Microsoft's in `imap/oauth/microsoft.rs`. For IMAP accounts, `imap::ImapOAuth` is the `AccessTokens` (access tokens kept until a minute before they expire; one refresh per account at a time, which concurrent callers share; `invalidate` forgets the kept one) and the sign-in: `sign_in(provider, address, open_browser)` and `sign_in_again(account, method, …)` run the browser flow with the address as login hint, refuse another account's sign-in with `SyncError::OtherAccount` (naming the one that signed in, keeping nothing), keep the secret, and return the `SignInMethod` for the account's settings (`OAuthSignIn`). `OAuthProvider::for_discovery` picks the provider: Google or Microsoft when discovery's `hosted_by` says so (the MX records or the servers found), otherwise none and a password, even when the provider's autoconfig lists OAuth2, as Postrinch has no client for it.
- **Google over IMAP** uses Google accounts' client (`google-oauth-client.json`) with the scopes `https://mail.google.com/ openid email` only, and without `include_granted_scopes`, so its grant is for mail alone. The address is learnt from userinfo and must be verified. Its refresh token is the IMAP account's own, under `postrinch.imap`; a Google account's under `postrinch.google` is read but never changed. Revoking a Google token withdraws the whole grant for the address and client, every token under it included, so every revoke goes through one check (`google::GoogleGrants::revoke_unless_shared`): a Google token is given back only when the other kind of account holds no Google token for the address (and, if the keychain cannot say, not at all: an unused token only lapses). That covers signing an IMAP account out, signing a Google account out, a Google account's refused sign-in, and an IMAP account's grant that failed the add-account check or was replaced (see The provider façade). A refused IMAP sign-in's token (another account, an unverified address) is always left to lapse.
- **An address is one account, a Google account or an IMAP account, never both.** The store keeps accounts by address, and the two would share Google's grant; Google mail is better added as a Google account. Each sign-in refuses an address that is the other kind with `SyncError::AlreadyAdded`, shown as "<address> is already added as a Google account" (or "… as an IMAP account"): `ImapOAuth::sign_in` before the browser opens, when `postrinch.google` holds a token for the address (for either provider); `GoogleAuth::sign_in` when `postrinch.imap` holds any secret for it (before the browser opens for a login hint, otherwise once userinfo names the address, and the new token is then revoked unless the IMAP account holds a Google grant). The store is checked too, for an account whose sign-in is not in the keychain: `postrinch_sync::check_address_free(store, address, provider)`. `sign_in_google` calls it (and on a refusal signs the new grant out, keeping nothing); the IMAP add-account flow must call it before it stores its account, password accounts included.
- **OAuth requests have timeouts**: every OAuth HTTP client (code exchange, refresh, userinfo, revocation; Google accounts' and IMAP accounts') comes from one constructor, `oauth::http_client`, with 10 s to connect and 30 s for the whole request (`OAuthTimeouts`; `with_timeouts` on `GoogleAuth` and `ImapOAuth` for tests). A provider that never answers fails the call, and the account's refresh lock is let go.
- **The loopback listener** serves its connections side by side, each with 5 s to send its request, so a browser's preconnect or the address of `localhost` it tried first holds nothing up. A connection that fails, sends something that is not a request, or asks for another path or state is answered (400, 404) or dropped, and listening goes on; the first redirect with the sign-in's state ends it, and the listeners close. A redirect with an error and no description names the provider ("Google answered …", "Microsoft answered …"). A token endpoint's success that does not parse is "the token endpoint's answer could not be read" (and userinfo's likewise), never serde's text, which could quote tokens.
- **Microsoft**: a public client, no secret; `https://login.microsoftonline.com/common/oauth2/v2.0/authorize` and `/token`; scopes `https://outlook.office.com/IMAP.AccessAsUser.All https://outlook.office.com/SMTP.Send offline_access openid email` (named again in token requests, as the v2 endpoint asks), a grant without the IMAP and SMTP scopes refused. The redirect is `http://localhost:<port>`, with no path: the listener is on that port of both 127.0.0.1 and ::1, as a browser may try either, and a port taken on ::1 is not used. The address is whichever of the ID token's `email`, `preferred_username` and `upn` claims is the address asked for, compared without regard to case (`email` may be an alias, and work accounts may lack it); when none is, the first of them that is an address, reported as `SyncError::OtherAccount`; the token's signature is not checked, as it comes straight from the token endpoint over TLS (OpenID Connect Core 3.1.3.7), and the mail server checks the access token against the user it signs in anyway. Microsoft rotates refresh tokens: a new one in a refresh answer replaces the kept one (if the keychain refuses it, the old one is kept, which Microsoft does not retire). Microsoft has no revocation endpoint for a refresh token; signing out removes the secret. Token errors are read by their AADSTS code (`error_codes`, or the description's prefix): 90094 and 90095 (admin consent required), 53003 (Conditional Access), 50105 (not assigned to the app), 53000 and 53001 (device not managed or compliant) are the admin's policy; 65001 (not consented), 65004 (declined), 50076, 50079 and 50158 (an interactive challenge such as MFA), 700082, 70008 and 70043 (refresh token expired), 50173 (grant revoked) and 70000 are a refused grant; 7000218, 700016 and 50011 are a misregistered client (`SyncError::Config`). Without a code, `invalid_grant`, `interaction_required` and `consent_required` are a refused grant. Each keeps the first line of Microsoft's description (not its trace and correlation ids). Any 5xx, and anything else, is a failure to try again.
- **The Microsoft client file**, `~/.config/postrinch/microsoft-oauth-client.json` (the platform's config directory; kept out of git like Google's): `{"client_id": "<the Entra application (client) id>"}`. `OAuthClients::load` reads both client files; a provider whose file is missing, or does not read, is not set up (`SyncError::OAuthNotSetUp`, shown as "Microsoft sign-in isn't set up in this copy of Postrinch", with the file's problem in brackets when there is one), and only that provider's accounts are affected.
- A refused login (`AUTHENTICATIONFAILED`, SMTP 535, or a refused refresh token) is the account's "needs to sign in" state with a sentence from the server, as for Google; Sign in again opens the browser for OAuth accounts and asks for the password otherwise. On IMAP the response code decides first (`imap/refusal.rs`): `AUTHENTICATIONFAILED`, `AUTHORIZATIONFAILED` and `EXPIRED` are a refused credential whatever the words, and only a refused credential gets an OAuth account its one fresh token. `CONTACTADMIN` is the admin's policy, not retried. `UNAVAILABLE`, `INUSE` and `LIMIT` are the server busy (`SyncError::Busy`, below). After signing in, a `NO` with one of them to the first commands (CAPABILITY, LIST), which name no folder, is the account's server busy too; to a later command, it is the account's only when the words name a known limit, `INUSE` and `UNAVAILABLE` otherwise only the folder's, and `LIMIT` not at all (see Sync). `ALERT` (which only asks for its text to be shown) and no code at all are read for their words: providers put real refusals and temporary limits under the same `[ALERT]`. A short table of known limit phrasings, matched anywhere in the text ignoring case (`TEMPORARY_LIMITS`, with sources), makes it busy: Gmail's "Too many simultaneous connections" and "Account exceeded command or bandwidth limits", Microsoft 365's "User is authenticated but not connected", Dovecot's "Maximum number of connections from user+IP exceeded" and "Temporary authentication failure". The same table (and for a `BYE`, the same three codes) also makes busy a `BAD` naming a limit, to LOGIN/AUTHENTICATE or to the CAPABILITY or LIST right after a sign-in that succeeded (where Microsoft 365 mostly sends it), and a `BYE` instead of the greeting or before sign-in (Dovecot turns a connection away at its limit that way); any other `BYE` is the server failing. Everything else under `ALERT` or without a code stays a refused credential, as Gmail's "Application-specific password required", "Please log in via your web browser", "Web login required" and "Your account is not enabled for IMAP use" are. Every other code (`SERVERBUG`, `CORRUPTION`, `PRIVACYREQUIRED` over a connection that is already TLS, and any code Postrinch does not know) is the server failing, to try again later: the account is not asked to sign in. On SMTP, 534 and 535 are a refused credential, as is AUTH's `432 4.7.12 A password transition is needed` (RFC 4954), which the person must act on, with the server's words; any other 4xx, at the greeting (`421`, then the server closes), EHLO, STARTTLS (`454 4.7.0 TLS not available due to temporary reason`) or AUTH (Gmail's `421 4.7.0 Try again later`, `454 4.7.0 Too many sign-in attempts`), is the server busy.
- **A busy server** (`SyncError::Busy { service, server, message }`) is neither "needs to sign in" nor a failure to report as one: no fresh token is fetched for it, and the add-account check says so (`CheckFailure::Busy`). The IMAP keep-in-sync and sending loops wait it out with `Backoff` and say so with `SyncEvent::Busy` (see Sync). An SMTP server that answers the error challenge's reply with another challenge has refused the sign-in; Postrinch cancels the exchange (`*`) and keeps the challenge's words. Fetching an access token is under the command timeout on both servers, so a provider that never answers cannot hang an account.
- **Credentials never reach the log.** async-imap logs every command it sends at trace level (LOGIN's password, AUTHENTICATE's base64 PLAIN or OAuth token) and every byte it reads (mail included), and lettre with its `tracing` feature logs SMTP's lines and AUTH challenges at debug; the `log` crate's records reach the same filter as tracing's. So every program (the app, `postrinch-cli`, `postrinch-mcp`) filters its log with `postrinch_log::filter` (`crates/postrinch-log`): `RUST_LOG` or the program's default, and also a second filter capping `async_imap`, `imap_proto` and `lettre` at info, which no `RUST_LOG` (not `trace`, not `async_imap=trace`) can raise. A library found to log secrets or raw protocol joins `PROTOCOL_TARGETS` there.

## The account's settings

`ImapSettings`, on the account in the store (no secrets): the IMAP host, port and security (TLS, STARTTLS), the SMTP host, port and security, the user name for each, how it signs in (password or a named OAuth provider), the folders chosen for each role when the person overrides SPECIAL-USE, and whether the provider files sent mail itself, with whether the person said so (`server_files_sent_chosen`). Plain-text connections are not offered.

In Settings › Accounts an IMAP account shows its servers and how it signs in, and has (`ui/imap_account.rs`, `imap_settings_run.rs`, after the mockup):

- **Server settings…** opens the add-account dialog's servers panel filled in with its servers. "Check and save" checks both with the sign-in the account keeps, and changes them only when both pass (`ImapSync::change_servers`): through `ImapSettings::servers_over`, so the roles and what sending learned stay, and the account's connections and busy waits are let go, as the next pass goes to the new servers. Back leaves the account as it was.
- **Sign in again…**, in place of Server settings… while the account needs to sign in. An OAuth account goes to the browser; a password account gets a dialog asking for the password (and the outgoing server's own, for one that has two), saying why it must sign in. Both go through `ImapSync::sign_in_again(oauth, account, SignInAgain::{Browser, Password})`: the password is checked against both servers and kept only once both take it, as when adding, and the account's servers and what was learned stay. One check runs at a time: Enter or Sign in again while the servers are checking asks nothing. The dialog's "Server settings" link opens the servers panel instead. `postrinch-cli sign-in` uses the same call.
- **Folders**: a choice per role (Sent, Drafts, Archive, Trash, Junk) among the account's folders but the inbox (`ImapSync::account_folders`, shown decoded; read off the window's thread when the account's page opens, and again after each pass of that account ends, while the page is shown: `AccountFolders::follow`), the first choice being the server's own ("Sent Items (the server says)", or "As the server says" once the person chose). A choice is kept in `ImapSettings.roles` (`ImapSync::change_folder_roles`, which changes only the role chosen, under the account lock, so two quick choices each keep theirs) and a pass runs at once, so the folders take their roles (see Sync for how a folder's label follows its role).
- **"The server files sent mail in Sent itself"**: what sync learned (see Writing and sending), until the person ticks or clears it (`ImapSync::set_server_files_sent(account, Some(on))`, which sets `server_files_sent_chosen`). A setting the person chose is never changed by what sending learns: no misses counted against it, no second copy turning it back on. "Let Postrinch notice again" hands it back (`None`), learned from where it stands.
- **Remove from Postrinch**, as for any account: its mail goes from this computer and its secret from the keychain; nothing is deleted from the server.

## Adding an account

From Settings › Accounts › Add account… (or the Account menu), which first asks which kind: Google (the Google account sign-in, as before), Microsoft (Outlook.com, Hotmail, Microsoft 365: the browser sign-in over IMAP, Microsoft's servers filled in when discovery finds none) or Other mail account. Google over IMAP is reached through Other mail account: discovery finds the domain's mail is Google's, the dialog offers "Add as a Google account" and, beside it, "Use IMAP anyway" (Google's browser sign-in over IMAP), the latter only when this copy has that sign-in. The HTML mockup is the design, `design/mockups/add-imap-account.html`; the dialog is `ui/add_account.rs`, `ui/add_account_sign_in.rs` (the found step's ways in) and `ui/add_account_servers.rs`, its state and steps `add_account.rs` (no window: what discovery fills in, what the form must hold), the slow work `add_account_flow.rs` and its running on sync's runtime `add_account_run.rs`. Nothing slow runs on the window's thread: discovery reports each step as it goes, and each of its reports and its answer carries the dialog's generation, so one for a lookup closed or gone back from is dropped. An add's answer is never dropped (`add_account_runs.rs`): the dialog shows it while the person is still waiting on that add, and once they have closed the dialog or moved on a notice says it was added, or why not (nothing, when they stopped the browser sign-in themselves). Only one add (or change of servers) runs per address at a time: asking again while one is under way says Postrinch is still busy with it. A second Enter or click while the dialog looks up, waits for the browser or checks asks nothing.

1. **Address and name.** Changing the address forgets everything found for the one before (servers, how it signs in, what was said of the provider, the trust given to its servers, the passwords typed), so the servers set up by hand are guessed from the new address. The address alone starts discovery, once `check_address_free` says it is not a Google account here (an IMAP account here already is signed in again by adding it, with what was learned kept).
2. **Discovery** (`crates/postrinch-discover`), in this order, first answer wins: the domain's own autoconfig (`https://autoconfig.<domain>/mail/config-v1.1.xml`, then `https://<domain>/.well-known/autoconfig/mail/config-v1.1.xml`), Mozilla's ISPDB (`https://autoconfig.thunderbird.net/v1.1/<domain>`), then the MX host's domain in the ISPDB (mail hosted by Google Workspace or Microsoft 365 is told so: Google's is better added as a Google account), then DNS SRV (`_imaps._tcp`, `_imap._tcp`, `_submissions._tcp`, `_submission._tcp`, RFC 6186/8314), then guesses (`imap.`/`mail.` and `smtp.`/`mail.` with the usual ports), each probed before it is offered. Everything over HTTPS; a plain-HTTP answer is refused. SRV records are not authenticated (RFC 6186 §6), so servers they name outside the address's domain are shown for the person to confirm before any password is sent (`Discovery::confirm_servers`).
3. **Sign-in**: "Sign in with <provider>" in the browser where Postrinch has an OAuth client for it, and nothing else (Google and Microsoft take no passwords); otherwise the password, or the app password with the provider's page for making one. A provider that signs in only in the browser, without that sign-in in this copy, has no way in: the dialog says so and asks for no password (`AddForm::no_way_in`, `Found::browser_only`), and `AddForm::to_add` refuses a password for it.
4. **Check**: Postrinch logs in to IMAP and SMTP (EHLO and AUTH, no mail sent) and lists the folders. Each failure says which server and what it said, in the server's words (two servers refusing alike say it once), with "<provider> needs an app password" after a refused password when discovery knows the provider's page. A refused password leaves the person where they gave it; a server that could not be reached, refused TLS or answered wrongly opens the manual settings with what was found filled in, their Back returning to where they were. Waiting for the browser can be cancelled: `NewSignIn::OAuth { cancel }` takes a `SignInCancel` (`sign_in_cancel()`), which stops only the wait for the browser's redirect, before anything is kept, so nothing is left half done (`SyncError::SignInCancelled`). Once the browser is back, `NewSignIn::OAuth { on_grant }` is told, and the dialog moves from "Finish signing in in your browser" to checking the servers, which offers no Cancel: the add runs to its end.
5. **Manual settings**, reachable at any time: both servers' host, port, security and user name; the password, and a second one for an outgoing server that has its own. The port is checked to be 1 to 65535 and each name to have no spaces before anything is sent.
6. The account is stored, its secret kept, sync and sending are woken (`SyncHandle::accounts_changed`), and its detail shows in Settings.

**Import from Thunderbird** sits beside Other mail account when Thunderbird profiles are found on this computer (looked for off the window's thread each time the dialog opens), and says how many accounts it can add. It lists every account in every profile (by profile when there are several, with the installation when they come from more than one) with its address, name, incoming server and how it would sign in, every account Postrinch can add ticked. Accounts already in Postrinch, an address already listed in another profile (addresses compared whatever their case), POP, newsgroups, feeds, Local Folders and other kinds are shown but cannot be ticked, each saying why; so is a Microsoft account when Microsoft's sign-in is not set up in this copy, and an account whose incoming or outgoing server signs in a way Postrinch cannot (Thunderbird's `authMethod` none, Kerberos, NTLM or a certificate; Google's and Microsoft's servers excepted, as Postrinch signs in to them its own way), each saying which server and how. A profile whose prefs could not all be read says so above its accounts, naming the file (`prefs.js` or `user.js`) and the first bad line, or why the file was refused. A Gmail or Google Workspace account (its IMAP server is Google's) is added as a Google account (Google's own sign-in, with labels and calendars), not over IMAP, even when Thunderbird signs in to it with a password (an app password); Microsoft accounts (Microsoft's servers) use the browser sign-in; every other IMAP account asks for its password, or its app password with the provider's page when Postrinch knows the provider needs one (`postrinch_discover::known_host`, from the server's name alone: no lookup runs). Passwords stay in Thunderbird: each chosen account is signed in to once, one at a time, "1 of 3", with Skip this account and Stop importing (which ends the whole import, the rest shown as not added). Change opens the servers panel and its Back returns to that account. An IMAP account goes through steps 3 to 6 exactly as one added by hand (`AddUi::add`: the same check, outcomes and servers panel; a failure stays on its turn); a Google account is handed to Google's sign-in, whose notice says how it went, and the next account comes up meanwhile. The dialog ends by saying which were added, skipped or not added. The servers are Thunderbird's own, so they are not confirmed again; a server Thunderbird reaches without encryption is tried with STARTTLS on the same port (Postrinch never signs in in the clear, and the check says so if the server offers none), and a server without a user name signs in with the address. Signatures are read (inline ones only) but not used yet, as Postrinch has no signatures. The state and steps are `import_thunderbird.rs` and `add_account_import.rs`, the dialog `ui/add_account_import.rs`.

**Reading Thunderbird's settings** (`crates/postrinch-thunderbird`, which reads files and nothing else): `profiles.ini` in `~/.thunderbird`, `~/snap/thunderbird/common/.thunderbird` and `~/.var/app/org.mozilla.Thunderbird/.thunderbird`, in that order, each profile's `Path` relative to that folder (`IsRelative=1`) or absolute, the default the one an `[Install…]` section names or, without one, `Default=1`; then each profile's `prefs.js` and, over it, `user.js` (whose prefs win, as when Thunderbird starts). A profile without a `prefs.js` (never used, or its folder gone) is left out. The prefs parser follows Gecko's grammar (`user_pref`, `pref` and `sticky_pref`; strings in either quote with `\\ \" \' \n \r \xHH \uHHHH` and surrogate pairs; 32-bit ints; bools; `sticky`/`locked`; `//`, `#` and `/* */` comments); a pref that does not parse is skipped to its `;` and counted by line, never quoted. The accounts are `mail.accountmanager.accounts` (or every `mail.account.<key>.server`), each with its server (`mail.server.<key>.*`: `type`, `realhostname` over `hostname`, `port` or the protocol's usual one, `socketType` 0/1 none, 2 STARTTLS, 3 TLS, `realuserName` over `userName`, `authMethod` as Thunderbird's `nsMsgAuthMethod`: 1 none, 2/3/4/8/9 passwords (3 when unset), 5 Kerberos, 6 NTLM, 7 certificate, 10 OAuth 2), its first identity (`useremail`, `fullName`, `htmlSigText` unless `attach_signature`) and that identity's `smtpServer`, or `mail.smtp.defaultserver` (`mail.smtpserver.<key>.*`: `hostname`, `port` or, as Thunderbird's SMTP client picks, 465 for TLS and 587 otherwise, `try_ssl`, `username`, `authMethod`). **Thunderbird's passwords and certificates are never opened, read or looked at** (`logins.json`, `key4.db`, `key3.db`, `signons.sqlite`, `cert9.db`): every read goes through one function (`files::read_settings_file`) that refuses any file but `profiles.ini`, `prefs.js` and `user.js` before touching it and refuses one of those that is a symbolic link (opened with `O_NOFOLLOW` on Unix, so the link's target is never opened; the person is told "user.js is a link, so Postrinch didn't read it"), or that is not a plain file, nothing lists a folder or asks for any other file's metadata (a profile folder may itself be a link: only settings files are read from it, by name), and the tests read the fixtures through a `Files` seam that records each path asked for, beside decoy password files, and check that no other source file of the crate touches the file system. The home folder is a parameter (`find(home)`), so tests and test windows point it at fixtures.

## Searching the server

A search whose words could be in mail not downloaded yet (headers only: the local index knows it by subject and people) also asks each account's server, once per query, as it always has for Gmail (`postrinch/src/remote_search.rs`; the line under the results names Gmail, the server or the servers). For an IMAP account the command layer translates the search language into IMAP's terms (`Commands::imap_search`, `postrinch-commands/src/imap_search.rs`, into `postrinch_model::ImapSearch`), and the IMAP engine asks it (`ImapSync::search_server`, `imap/sync/search*.rs`).

- **A superset, checked here.** What the server is asked must find at least what the query matches; what it finds is then checked here against the whole query (`Commands::server_found_holds`, `search_remote.rs`, which the app hands the IMAP engine as its `Holds` and `Commands::remote_rows` applies again: the store's search narrowed to the messages found; those stored by their headers alone are checked by everything but their words, which the server matched in the body), so what IMAP cannot say exactly never shows wrong results. Words are read as search here reads them, by the `english` analyzer (`postrinch_store::search_tokens`, `search_terms.rs`): each word, and each term of a phrase or a hyphenated word (`invoice-4471` is `invoic` and `4471`), is a `TEXT` of its own, all of them required, and each `TEXT` is the stem cut back to what every word of that stem contains (`server_texts`: `shipping` asks `ship`, `happiness` `happ`, `probably` `probab`, with the stemmer's few irregular forms, `dying` and the like, asked as an `OR`). `TEXT` is a substring match, so this finds at least what search here finds, and the check here drops what only shares the letters (`relationship` for `shipping`). A stop word asks nothing. A word not in ASCII is asked as far as its letters typed match its stem (`café` asks `caf`): accents in the mail are matched as the server matches them, which may be more or fewer than search here folds. `-word` is not asked: `NOT TEXT` would leave out mail search here keeps (`-cat` would leave out "concatenate"). It is checked here instead, by the same analyzer (`Find::text_without`): what has the word in a downloaded body, or in the subject or people of one stored by its headers, is left out; a word left out that is only in a body not downloaded yet cannot be checked until the body is here, so such a message shows. Nothing left out is ever asked, people no more than words: `-from:`, `-to:`, `-cc:` and `-bcc:` send no `NOT FROM`/`NOT TO`, as a server matches addresses and names its own way (Dovecot folds accents, so `NOT FROM "jose"` would leave out "José", whom search here keeps); they are checked here, as search here reads them (`Find::not_from`, `Find::not_to`). There is no `NOT` key at all (`postrinch_model::SearchKey` has none), so what the server is asked stays a superset. `-label:` is no key but a folder not looked in: a message with a copy there has that label here, so the check leaves it out as well. `from:` `FROM`, `to:` `OR TO (OR CC BCC)` (the local `to:` covers all three), `subject:` `SUBJECT`, `is:unread`/`is:read` `UNSEEN`/`SEEN`, `is:starred`/`is:unstarred` `FLAGGED`/`UNFLAGGED`, `larger:`/`smaller:` (`size:`; `K`, `M`, `G` are binary) `LARGER`/`SMALLER`. Dates (`after:`, `before:`, `newer_than:`, `older_than:`) are `SINCE`/`BEFORE` days widened by two each way, as IMAP's are whole days in the server's zone, matched against when the server received the copy, not the `Date` header. `last:` and every label after the first are left to the local check. An `OR` of the language (`{a b}`, `OR`) is one alternative each, joined by `OR` in each folder they share.
- **What IMAP cannot ask.** `has:attachment` has no IMAP key (`BODYSTRUCTURE` is not searchable): on a plain IMAP server the search is refused before anything is asked (`SyncError::SearchRefused`, "IMAP has no way to ask for has:attachment"), and the results are the mail here. On Gmail's servers (`X-GM-EXT-1`) every alternative is asked in Gmail's own language with `X-GM-RAW`, `has:attachment` included, less the words and people it leaves out (`Query::gmail_superset`: `-word`, `-from:`, `-to:`, `-cc:`, `-bcc:`), for the same reason as above (Gmail folds accents too). `-label:`, `-in:` and `-category:` stay in what Gmail is asked: only All Mail is searched and a copy stored by its headers does not know its labels (nothing fetches `X-GM-LABELS`), so the check here could not leave them out, and `rota -in:inbox` would show inbox mail. Gmail folds case, `/`, `-` and spaces in label names, so `-label:a-b` may also leave out mail labelled "a b", which search here keeps: rarer, and the smaller loss. An alternative with nothing left to say in Gmail's language (`-from:jose` alone, `last:me`) asks `ALL`.
- **Strings.** Printable ASCII is a quoted string (`\` and `"` escaped); anything else a literal (`{n+}` with LITERAL+), with `CHARSET UTF-8` before the keys. A server that refuses that charset (`NO [BADCHARSET]`) gets a sentence ("it cannot search for text that is not plain ASCII"), and the results stay the mail here.
- **Folders.** An alternative with `in:` or `label:` looks in that folder; one without looks where a search covers: every folder but those with the Trash and Junk roles (they too with `in:trash`, `in:spam`, `in:anywhere`), the inbox first, by the account's folder roles. On Gmail's servers that is All Mail alone, plus Trash and Spam when asked: the folder LIST marks `\All` (the search lists the folders first to know it, `folders::holds_everything`), whichever folder is the archive, since the person may make another folder the archive and All Mail still holds every message. `-in:`/`-label:` folders are not looked in.
- **A page of what holds, newest first.** A page is 50 (`REMOTE_MAX` in the app) messages that pass the check, not the 50 newest found less those that do not: as the server is asked a superset, `invoice -from:billing` (asked `TEXT invoice`) could otherwise find only billing's newest 50 invoices and show nothing. Each folder gives every UID it found, and the page walks them newest first (`search_walk.rs`, `search_page.rs`): from each folder's top a batch at a time, merged across folders by arrival, as many as the page still needs per batch; the batch's copies not stored are fetched by their headers and stored, the check (`Holds`) keeps those that hold, and the next, older batch follows until the page is full or the found run out. The walk looks through at most ten found messages per page slot (500, `LOOKED_PER_SLOT`), so a search the check narrows hard (`ALL` with only `-from:` to say) cannot fetch a whole mailbox. The bound counts the messages walked into a batch, newest first across every folder (a copy of a message already checked is walked past and not counted), never the UIDs taken from each folder to have its next few in hand: every folder with finds left has some in hand before the newest is chosen, however many folders there are, so the newest finds are walked wherever they are. When the bound stops the walk with the page not full and finds not walked yet, `ServerFound::looked_through` says so and the line adds "only the newest 500 of the messages it found were looked through; older ones may match too". A message is marked checked only once a copy of it is stored and checked, so when one copy's folder is busy another folder's copy stands for it. Copies the store has are known by their place; when several folders found more than a page, the others' `INTERNALDATE`s and `Message-ID`s are fetched as each batch is taken, to keep the newest across folders, a page slot for each message, not each copy: a message in the inbox and an archive takes one, the copy the store has standing for it. A newer search can take the connection between any two batches. Copies not stored yet are fetched by their headers (`fetch_headers`, as a pass reads new mail) at the UIDVALIDITY the folder was searched at, and stored as a pass stores them, so they show and open as any message (bodies on opening, or by backfill), and the next pass finds them kept. The search has a connection of its own (`Lane::Search`), so it never waits behind a pass and opening a message never waits behind it. A newer search of the account takes an older one's place: the older one stops before its next command (`SyncError::SearchSuperseded`, never shown) and leaves the connection to it. A hit opens in any case: bodies are fetched from a copy whose UIDVALIDITY `SELECT` confirms, so a copy found in a folder no pass has read yet, or after its UIDVALIDITY changed, opens too, the folder's state left for the pass, and a copy that cannot be fetched gives way to the message's next one (`bodies.rs`).
- **Busy and refused.** A server busy for the account is `SyncError::Busy` ("The server is busy, so mail not downloaded yet is searched by subject and sender only"), never a sign-in, and a server whose busy wait is still running is not asked. A folder busy (`[INUSE]`, `[UNAVAILABLE]`) or refusing the search (`NO`, `BAD`) is left out, and the line says so ("1 folder was not searched (…)"); refused in a folder and nothing found, the search is `SearchRefused` and the line gives the server's words; every folder busy is `SyncError::Busy` for the folders (the account's busy wait is left alone), so the line says the server is busy. With several accounts asked, each account's outcome stays on the line (`remote_search::Note`): what one could not search, or why its server was not asked, is named by its account beside what the others found, and when none could search the line says why for each.
- **Agents.** The `search` tool's `not_downloaded` lists IMAP accounts as it lists Google ones: accounts with mail whose words were matched only against subject and people.

## The provider façade

The app and `postrinch-cli` hold one `MailSync` (`postrinch-sync/src/mail/`), which has the Gmail engine when Google is set up and the IMAP engine always, and sends each call to the account's provider: sync, backfill, download now, the outbox and outgoing mail, labels (an IMAP account's folders) and letting go of connections. Keeping in sync and sending (`MailSync::keep_in_sync`, `keep_sending`) run Gmail's loops as they were beside one loop per IMAP account and duty, accounts concurrently: each polls on the interval, is woken by Sync now, sends the outbox and outgoing mail after a change made here, and waits out a busy server (see Sync). A missing Google OAuth client turns off Google accounts only: the window says so in the sidebar only when the store has Google accounts, and IMAP accounts sync all the same.

What only Google has stays Google's. `MailSync::calendar` hands a Google account's calendar calls to the Gmail engine and refuses an IMAP account's (`SyncError::NoCalendars`); the commands refuse them first (`Commands::check_calendars`), so an agent's calendar call for an IMAP account gets a sentence saying so. Asking the server to search is `MailSync::search_server`: Gmail's search for a Google account, `UID SEARCH` for an IMAP one (below). The agents crate's `Gmail` trait is now `Remote` (`postrinch-agents/src/remote.rs`), the same calls, which the app implements over the façade (`postrinch/src/remote_mail.rs`).

Adding, signing in again and removing an IMAP account are `ImapSync::add_account`, `sign_in_again` and `remove_account` (`imap/sync/accounts.rs`), shared by `postrinch-cli add-imap` and the window's add-account dialog. Adding refuses an address that is a Google account here before anything opens, checks both servers, and keeps the secret only when the check passed: a password, or the OAuth grant the browser sign-in made, which the check uses without its being kept anywhere (`ImapOAuth::grant`, then `keep`). A failed check so leaves an account already here exactly as it was, secret and settings both; its grant is given back unless the account's own secret is a grant with the same provider, which may be the same grant (with Google, revoking one token withdraws them all). Adding an account that is already here (add-imap run again, signing in again with a password) changes only its servers, ports, security, user names and sign-in (`ImapSettings::servers_over`): the folder roles the person chose and what sending learned (`server_files_sent` and its back-off state) stay, read and written under the store's account lock (`Store::change_account`) so nothing sending learns meanwhile is lost. When the new secret replaces an OAuth grant (a password over an OAuth account, or another provider's grant), the old grant is given back once the new secret is checked and kept; one replaced by a grant with the same provider is not, as with Google that would withdraw the new one too. The old secret is read, the new one written and the account stored with the account's access-token slot held (`ImapOAuth::replacing`, `imap/oauth/replace.rs`), the lock a refresh holds while it keeps a refresh token the provider rotated (Microsoft rotates on every refresh): so no rotated token lands over a new password, and the grant given back is the one actually replaced. If the secret cannot be kept or the account stored after a passed check, the old secret is put back and a new grant is given back under the same rule as after a failed check. Signing in again marks the account signed in under the store's account lock too (`Store::update_account`). After a browser sign-in, or a removal, the app wakes both the sync and the sending loops (`SyncHandle::accounts_changed`), so mail that waited while the account had to sign in goes at once; `postrinch-cli` runs no loops, so its sign-ins have none to wake.

## Testing

A pure-Rust fake IMAP and SMTP server (`crates/postrinch-mailtest`, a dev-dependency only) runs in each test on a loopback port, with in-memory folders, UIDs, MODSEQs and the extensions under test switchable (CONDSTORE, QRESYNC, MOVE, UIDPLUS, SPECIAL-USE, LIST-EXTENDED, IDLE, OBJECTID, LITERAL+), plus FETCH answers split in two or mixed with unsolicited flag updates, IDLE that tells of changes as they are made (with a count of sessions idling, a `BYE` to end their IDLEs, and each `DONE` logged), a limit on each user's signed-in sessions answered `NO [LIMIT]` as Dovecot's (which can be set mid-test, and which LOGOUT frees before it answers), faults that answer `OK` without running a command, folders hidden from LIST, faults on a command whose text matches, and hooks that change the mailbox when a command arrives; switchable too are the SASL mechanisms offered (PLAIN, XOAUTH2, OAUTHBEARER) and whether the plain-text port offers STARTTLS at all, plus TLS with a test certificate. No test touches a real mailbox.

**The smoke test against a real server**, GreenMail (a third party's IMAP and SMTP server, so what Postrinch and the fake both took for granted is checked against someone else's reading of the RFCs), is `crates/postrinch-sync/tests/greenmail/`. One account through the code the window and `postrinch-cli` use (`ImapSync::add_account`, then the `MailSync` façade): added with a password (both servers checked, the secret kept), synced, its mail read, starred, archived, trashed and moved, each seen on the server by another client (async-imap of its own, not Postrinch's IMAP code), a sync after agreeing; mail sent over SMTP arriving in another user's inbox and filed in Sent; and the server's search finding mail not downloaded yet, its word only in the body, and not what is in the trash. The test starts GreenMail's standalone jar with `java` on two free loopback ports (IMAPS and SMTPS), with a CA and a certificate for 127.0.0.1 made for the run by `keytool`, which only the test trusts, and kills that process when it ends; the store is in a temporary directory and the secrets in memory, never the real store or keychain.

It needs a JDK (17 or later) and the jar, so it is `#[ignore]`d. `tools/greenmail-smoke.sh` downloads the jar from Maven Central once (into `~/.cache/postrinch/greenmail`), checks its SHA-256 against the one pinned in `tools/greenmail.pin`, retrying when Maven Central is busy, and runs the test (`--release`) with `POSTRINCH_GREENMAIL_JAR` naming it; `CARGO=cargo-alt` builds it in the second build directory. Run with `--ignored` without that variable, the test fails saying what to run: it never passes without a server. CI runs the script as its own job (`greenmail` in `.github/workflows/ci.yml`, Temurin 21), caching the jar under a key made from the pin. Moving to a newer GreenMail is the `version` and `sha256` in `tools/greenmail.pin`.

The add-account dialog's whole add is tested through the code the window calls (`add_account_flow_tests.rs`). To walk the window itself against the fakes, `cargo run --release -p postrinch-mailtest --example serve -- <dir>` keeps both servers running (user `ada@example.org`, password `correct horse`, a Sent, Drafts and Trash, two plain folders and one message), prints their ports and writes their certificates to `<dir>/certs.pem`. A test copy of the window started with `SSL_CERT_FILE` set to that file trusts them; the account is added by hand with server 127.0.0.1 and the printed ports. Creating `<dir>/refuse` makes IMAP refuse the next sign-in, so the account needs to sign in again on its next new connection (start the window again to make one).

Importing from Thunderbird is tested on the fixture profiles in `crates/postrinch-thunderbird/tests/fixtures` (normal, Snap, Flatpak, several profiles, OAuth Gmail and Microsoft, password IMAP, POP and other kinds, a damaged `prefs.js`, beside decoy password files), through the code the window calls (`import_thunderbird_tests.rs`, `add_account_import_tests.rs`), and end to end against the fakes in `add_account_flow_tests.rs`. To walk it in the window, start the test copy with `HOME` pointing at a folder holding a copy of a fixture's `.thunderbird` (never your own home, whose Thunderbird is real), with a profile whose `prefs.js` names 127.0.0.1 and the printed ports for an IMAP account: the import finds it as it would a real one.

Server search is tested against the fake (`postrinch-sync/tests/imap/search.rs`): mail not downloaded yet found and stored, the page across folders, Trash and Junk left out, named folders, a busy folder and a busy account, `BADCHARSET` (the fake's `ascii_search`), `has:attachment` refused, and Gmail's `X-GM-RAW` in All Mail (the fake takes `X-GM-RAW` when it says it is Gmail). The translation's own tests are `postrinch-commands/src/imap_search_tests.rs` and `postrinch-sync/src/imap/sync/search_keys.rs`.

## Crates

- **IMAP: `async-imap`** (tokio runtime, used in production by Delta Chat), with `tokio-rustls` and `rustls-platform-verifier`, as reqwest already uses. Raw commands for what it lacks (`UID MOVE` parsing of COPYUID, `ENABLE QRESYNC`). The greeting, CAPABILITY and STARTTLS are spoken by Postrinch before async-imap takes the TLS stream (nothing read before STARTTLS may be left in the buffer), and the sign-in's tagged reply is read from the bytes the stream recorded, as async-imap keeps only a debug string of a NO: that is how a refusal keeps the server's own sentence. The trust store is the platform's, with extra roots only where a caller adds them (`TlsConfig::with_extra_roots`, for the tests); there is no way to accept a certificate that does not verify.
- **SMTP: `lettre`** without default features: `smtp-transport`, `tokio1-rustls`, `rustls-platform-verifier`, `aws-lc-rs`. The message bytes are still built by `mail-builder` (`build_message`), and sent raw. AUTH is spoken over lettre's connection rather than by lettre (its XOAUTH2 takes Google's error challenge for a protocol error, and it has no OAUTHBEARER); only LOGIN, for servers offering nothing else, is lettre's. EHLO names lettre's default client id, not the machine.
- **Mailbox names**: Postrinch's own modified UTF-7 decoder (`imap/sync/utf7.rs`), as `utf7-imap` panics on a malformed name. **DNS SRV and MX: `hickory-resolver`**. **Autoconfig XML: `quick-xml`**.
